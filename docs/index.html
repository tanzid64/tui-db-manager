How it works

From install to restore in 5 steps

Everything happens in the dbk screen with a few keys. Each step also shows the matching command, if you prefer scripts.

1. Install dbk

Run the install command on your server (over SSH, or cPanel → Terminal). It also creates a ready-to-use storage called local at ~/dbk-backups, so there's nothing else to set up before your first backup.

terminal
$ curl -fsSL https://raw.githubusercontent.com/tanzid64/tui-db-manager/main/install.sh | sh
==> Downloading dbk v1.1.0 for linux/amd64...
==> Checksum verified
==> Installing to /usr/local/bin/dbk...
==> Setting up dbk (database + default local storage)...
default local storage "local" -> /home/you/dbk-backups
==> Installation complete! Run 'dbk' to start.
  • Then start it: type dbk and press Enter.
  • Move around with ↑ ↓, open with Enter, go back with Esc.
⚠

If the installer says ~/.local/bin is not in your PATH (common on cPanel), run ~/.local/bin/dbk, or add export PATH="$PATH:$HOME/.local/bin" to ~/.bashrc.

2. Add your database

Open Backup Jobs and press a. A short form asks four things. Your password is stored encrypted on the server and never shown in process lists.

dbk › Backup Jobs › Add
Add New Backup Job — Step 2 of 4: Server Connection
Connection parameters for the database server

▶ Host:     127.0.0.1                    
  Port:     3306
  Username: myaccount_shop
  Password: ••••••••
  [ ] Use TLS

Tab/↓ Next • Enter Next/Submit • Esc Back
  • Name & type — any name (e.g. shop), then MySQL/MariaDB, PostgreSQL, MongoDB or SQLite (← → to choose).
  • Connection — host, port, user, password. Ports and users fill in for the type you picked.
  • Database — dbk lists the databases it can see; pick one.
  • Storage & keep — local is preselected. Keep last 7 backups, gzip compression and Encrypt backups are on by default.
🔑

Encrypted backups need their key to restore. The key is kept on this server. After adding a job, save a settings backup somewhere else, so you can restore even if the server is lost.

💡

On cPanel, use the database user cPanel created (it starts with your account name, like myaccount_shop) and host localhost or 127.0.0.1.

Prefer files? Import jobs from a bundle, then store the password:

$dbk config import jobs.yaml
$dbk secret set job/shop/password --stdin

3. Test it and back up now

In Backup Jobs, select your job. Press t to check the database connection, then Enter to run a backup right away.

dbk › Backup Jobs
Backup Jobs
Each job backs up one database to a storage

▶ shop   (mysql → local, keep 7, not scheduled) [gz] ✔ OK

✔ Backup saved: shop/shop-20261025-030000.sql.gz (12.1 KB, 1.2s)

Enter/r Back up now • t Test • a Add • e Edit • d Delete • b Restore
  • Backups are saved as <job>/<job>-<date>-<time>.sql.gz in the job's storage.
  • Older backups beyond "keep last" are deleted automatically.
  • Every run — manual or scheduled — appears under History, with the error if it failed.

Same thing from the command line:

$dbk test shop
$dbk run shop

4. Schedule automatic backups

Open Schedules, select the job, press Enter and pick how often. It keeps running after you log out — on a VPS and on cPanel.

dbk › Schedules
Automatic Backup Schedule
How often should shop be backed up?

▶ Frequency: [Every day at 03:00]  Every 12 hours  Every 6 hours
             Every hour  Every Sunday at 03:00  Custom (cron expression)
  Custom cron (only for Custom): 30 2 * * *

✔ "shop" will back up every day at 03:00 (via crontab).
  Log: ~/.config/dbk/logs/shop.log
  • Use ← → to pick a frequency. Want something else? Type a cron expression such as 30 2 * * * (2:30 every night).
  • Turn a schedule off with x.
  • Each scheduled run writes to ~/.config/dbk/logs/<job>.log — the first place to look if something's off.

From the command line:

$dbk schedule install shop --at "0 3 * * *"
$dbk schedule status shop

5. Restore a backup

Open Restore, pick the job, then pick a backup — newest first, from every storage you've used. Type RESTORE and press Enter.

dbk › Restore

  2026-10-24 03:00  12.0 KB  [bucket] shop/shop-20261024-030000.sql.gz
  2026-10-20 03:00  11.8 KB  [local]  shop/shop-20261020-030000.sql.gz

↑/↓ Navigate • Enter Select • Esc Back
  • The restore replaces the current data in that database, so dbk asks you to type RESTORE first.
  • Want to check a backup without touching live data? Press Tab on the confirm screen and enter a different database name to restore into.

From the command line (latest backup, or a specific one):

$dbk restore shop --yes
$dbk restore shop --yes --at shop/shop-20261020-030000.sql.gz

Storage

Where should your backups go?

Start with the local folder — it's already set up. For off-server safety, add a bucket or Google Drive and switch your job to it.

💾

Local folder Ready

Created on install at ~/dbk-backups. Fastest, nothing to configure — but it lives on the same server.

🪣

Bucket (S3-compatible)

AWS S3, Cloudflare R2, Backblaze B2, MinIO, Wasabi. Keeps copies safe even if the server is lost.

📁

Google Drive

Uses a service account — no browser login, so it works for scheduled backups.

🔁

Switching storage later is safe. Edit the job (e) and pick the new storage. Older backups stay where they are and still show up in Restore, labelled with their storage. Just don't delete the old storage while you still need them.

VPS & cPanel

Works the same on both

dbk runs as your normal user and schedules backups with crontab, which exists on virtually every VPS and on cPanel shared hosting.

🖥️ On a VPS

  • Install the database client tools if they're missing:
    sudo apt install mariadb-client or postgresql-client (or mongodb-database-tools).
  • Run the install command as the user who should own the backups.
  • Schedules keep running after you close SSH — no need to stay logged in.
  • Check a schedule any time: dbk schedule status <job> or crontab -l.

🌐 On cPanel

  • Open cPanel → Terminal (or SSH) and run the install command. No root needed.
  • Use the database user from cPanel → MySQL Databases (e.g. account_dbuser), host localhost.
  • No special privileges needed — dbk skips the server-wide data (tablespaces) that shared hosting doesn't allow.
  • Your schedule appears in cPanel → Cron Jobs. Don't edit that line by hand; change it in dbk.
⚠

Backups on the same server aren't enough on their own. If the server or hosting account is lost, so is ~/dbk-backups. Add a bucket or Google Drive for important databases.

Security

Your data stays yours

dbk runs on your server. No account, no outside service, and no one else sees your passwords or backups.

🔒

Encrypted backups Default

New jobs encrypt every backup with age before it leaves the server. S3, R2 or Google Drive only store unreadable .age files. Jobs that send unencrypted backups to the cloud are marked ⚠ not encrypted.

🗝️

Random master key

Each install gets its own random key that protects saved passwords (XChaCha20-Poly1305, Argon2id). Upgrading from 1.0.0 switches you to a random key automatically. Your schedules keep running.

🙈

Passwords stay hidden

Database passwords go to the dump tools through environment variables, never the command line, so other users can't see them in ps. Schedule scripts don't contain your key.

📂

Private files

Settings, the password vault, logs and local backups are readable only by your user (0600/0700).

🏠

Nothing leaves without you

No sign-up, no tracking, no third-party backup service. Backups go only to storage you add.

✅

Checked updates

dbk update verifies the download's SHA-256 checksum before replacing the program.

Back up your settings (and your keys)

Your backups are only half the story. To restore on a new server you also need your jobs, storages, passwords and the encryption keys. Save them in one file, protected by a passphrase you choose. Do this after adding or changing a job.

In the app

  • Open Settings → Export Settings Backup.
  • Keep Include passwords & encryption keys ticked and enter a passphrase. Remember it: you'll need it to import.
  • dbk saves ~/dbk-settings-backup.yaml. Copy it off the server (your computer, a password manager, a different bucket).
  • On a new server: install dbk, then Settings → Import the file with the same passphrase. Your old backups show up in Restore.

From the command line

Save settings, passwords and keys (asks for a passphrase)
dbk config export ~/dbk-settings-backup.yaml --include-secrets
Copy it to your computer (run this on your computer)
scp user@server:dbk-settings-backup.yaml .
Restore on a new server (asks for the passphrase)
dbk config import dbk-settings-backup.yaml
⚠

Don't keep the settings backup only on the same server or in the same bucket as your backups. Anyone with both the file and its passphrase can read your backups, and if the server is lost with the only copy, encrypted backups can't be restored.

Help

Common questions & fixes

My scheduled backup didn't run. Where do I look?

Open the job's log — every scheduled run writes its start, result and any error there:

$tail -n 30 ~/.config/dbk/logs/shop.log

If the log has nothing new, check the schedule is installed with dbk schedule status shop. In Schedules, a ⚠ next to a job means it's saved but not installed — press Enter on it to fix.

"required client tool not found"

dbk uses the database's own dump tools. Install them on the server: mariadb-client or mysql-client (MySQL/MariaDB), postgresql-client (PostgreSQL), mongodb-database-tools (MongoDB), sqlite3 (SQLite). cPanel servers already have the MySQL tools.

The storage test failed

dbk writes, reads back and deletes a small test file. A failure usually means a wrong secret key (403 / Forbidden), a bucket name or region that doesn't match, or an endpoint pointing at a web console instead of the S3 API. Press e on the storage to fix it, then t to test again.

I moved my job from local to S3. Where are my old backups?

Still in the old storage. Restore lists backups from every storage, labelled [local], [bucket] and so on. From the command line, dbk list shop shows the storage in the last column, and dbk restore shop --yes --storage local restores the newest one from there.

Can I restore into a test database first?

Yes. On the confirm screen press Tab and enter another database name, or use dbk restore shop --yes --to shop_test. The target database must already exist.

Where are my passwords stored? Are they safe?

In ~/.config/dbk/dbk.db, encrypted with a random master key that's unique to your install (saved in ~/.config/dbk/env). Both files are readable only by your user. Passwords are passed to the dump tools through environment variables, never on the command line, so other users can't see them in the process list. See Security.

My server died. How do I restore my encrypted backups?

You need your settings backup file and its passphrase. On the new server, install dbk and import it:

$dbk config import dbk-settings-backup.yaml

Your jobs, storages, passwords and keys come back, and Restore lists the backups in your bucket. Without the settings backup, encrypted backups can't be opened, so save one today.

I updated from 1.0.0 and see "replaced the default master key"

That's expected and only happens once. Version 1.0.0 used the same built-in key on every install. 1.1.0 replaces it with a random one, re-encrypts your saved passwords and updates your schedules, which keep running. Nothing to do, but it's a good moment to save a new settings backup.

How do I update dbk?

Run dbk update. Your jobs, storages and schedules are kept.

Coming from an old pre-1.0 build (v1.1–v1.6)? Re-run the install command once — those builds don't see 1.0.0 as newer.

How do I remove dbk completely?

This removes all schedules, settings and the program. Your backup files in ~/dbk-backups and buckets are not deleted.

$dbk uninstall --all --yes

dbk test shop
